## Hard rules

- **Do not take any action AJ has not explicitly requested.** Propose changes and wait for approval before making them. If solving a stated problem seems to require a side change (removing a block, restructuring a file, touching an unrelated area), stop and ask first -- never assume. An assumption that turns out to be wrong wastes time and creates trust debt.

- **`npm run dev` is a blocking process that never exits.** Never chain it with `&&` after other commands. Always run it alone, standalone, in its own terminal step.
- **Every terminal command must start with `cd ~/Sites/[repo-name]`**: AJ works from one terminal window across multiple repos; never assume the working directory.
- **Finish the work in the session.** Never suggest deferring a task to "a later session": there is no later session.
- **This platform is built on CQC's Adult Social Care sector-differentiated framework (draft), NOT the Single Assessment Framework (SAF).** The SAF is CQC's cross-sector framework for NHS and other providers. Every piece of content must reference only the Adult Social Care framework.
- **Run migrations immediately after committing them: on BOTH the preview and production Supabase projects.** The deploy workflow applies app code only; Vercel does not run schema changes, and there is no CLI-tracked migration table, so a migration run on only one project is invisible drift until something breaks or a security fix silently doesn't apply everywhere. `.env.local` has direct Postgres connection strings for both (`SUPABASE_PREVIEW_DB_URL`, `SUPABASE_PRODUCTION_DB_URL`, both session-pooler URLs, since this environment can't reach Supabase's direct/IPv6-only host). Run the migration file against both directly (e.g. via `pg`) rather than asking AJ to paste SQL into the Supabase SQL Editor. Order: write migration → run on preview → run on production → verify it applied on both → commit → push to GitHub. Never let migration files accumulate unrun, and never consider a migration "done" after running it on just one project. If `SUPABASE_PRODUCTION_DB_URL` is ever missing (a fresh environment, a rotated password), fall back to asking AJ to run it in the SQL Editor instead of guessing or skipping production.
- **`lib/types.ts` is hand-maintained, not auto-generated.** Any migration that adds, removes, or renames a column needs a matching update to that table's `Row`/`Insert`/`Update` blocks in `lib/types.ts`, in the same commit as the migration. Run `npx tsc --noEmit` afterward to confirm.
- **Writing marketing copy or content about a platform feature?** Read `docs/FEATURE_MAP.md` first, then the relevant code folder. The codebase is the ground truth: not handoff docs, not memory, not assumptions.
- **Asked about a third-party dashboard setting (Supabase, Stripe, Vercel, Cloudflare, Resend, etc.) and don't know its exact current location?** Say so immediately and search for it; never guess a navigation path.
- **No em dashes anywhere you write for this project**: commit messages, code comments, documentation, or copy. Use proper punctuation instead (colon, comma, semicolon, or a new sentence).

## Debugging schedule

This repo has a living audit schedule tracked in [Issue #23](https://github.com/ethna-p/alwaysready-inspection-readiness-platform/issues/23): a 7-chunk checklist (auth/session, data flow, uploads, cron, RLS, security, schema drift) plus a standing recommendation to periodically run an open-ended `/code-review` alongside it, since the chunks only catch patterns already seen once before. Read that issue before a scheduled audit pass, and amend it (new chunk, new check, dated update note) whenever a pass finds a category of bug the existing chunks didn't cover.

### Standing discipline for Playwright walkthroughs and general audit work

1. Finish all work before moving to new work.
2. Verify every Playwright action, no matter how small — every click, every form fill, every page load — not just that it didn't throw. The real failure mode is a silent no-op, not an exception: a click can land on the wrong element (`document.querySelector('button[type="submit"]')` grabs the *first* match in DOM order, which might be "Sign out" in the header rather than the form's own submit button — scope the query to the specific `<form>` instead of the whole page), or miss its target because a custom viewport doesn't match the actual interaction coordinate frame, and the network tab still shows `200 OK` because *some* request went through, just not the one that was meant. After every action, confirm the thing actually expected to change did change: re-query the DOM (or check `.value`/`.disabled`) right after a fill or click rather than assuming it registered, confirm the *specific* request fired rather than just any 200, and where there's a database behind the UI, check it directly rather than trusting a success toast or status message.
3. When an audit flags a new bug, issue, or concern, do not just log it as a new GitHub issue and move on. Finish the item currently in progress, then come straight back and fix the newly found one in the same session.
4. After isolating and fixing a new issue, re-run that specific fix three times to confirm it's stable, then run the full e2e suite once to confirm nothing else was destabilised. Exception: an e2e spec that mutates the shared fixture org (most of them do) isn't safe to re-run back-to-back without re-seeding between runs, several don't fully revert every side effect, so a second consecutive run can fail for reasons that have nothing to do with the fix and everything to do with the first run's leftover state. For those, re-seed (`npm run test:e2e:seed`) before each repeat, or treat one clean pass as sufficient confirmation rather than manufacturing a false failure by repeating it raw.
5. If a system or codebase anomaly turns up that doesn't fit anything already understood, don't ignore it: flag it, finish the item in progress, then come back and fix the anomaly too.
6. Whenever a fix can be verified by AJ logging in as superadmin, admin, user, or viewer, say so explicitly, so she can confirm it from that perspective herself.

**Recognize fixture drift before chasing a false regression.** Most e2e specs share ONE fixture org and user set (from `npm run test:e2e:seed`) rather than each getting a fresh isolated org. Any spec that mutates shared state (subscription tier, sub-service toggles, KLOE ratings, etc.) and then fails or gets interrupted before its own cleanup step leaves that drift behind for the next spec to trip over — and several specs don't fully revert every side effect even on a clean pass, so running the same spec (or set of specs) twice in a row without re-seeding between can fail for that reason alone. This is purely a testing-infrastructure artifact, confined to `__E2E_TEST_ORG__` in the preview database: it has no bearing on the real product or real customers, who each get a genuinely isolated organisation with real RLS tenant isolation, no shared-org mechanism exists outside this test fixture. Tell: a cluster of unrelated-looking specs failing together, rather than one focused failure, especially right after running the same mutating spec multiple times in a row or interrupting a test mid-run. Fix: re-seed (`npm run test:e2e:seed`, which deliberately wipes and recreates rather than trying to patch partial state) before spending time chasing individual failures as if they were real regressions.

**A second, related trap: real rate limiters, not just fixture data, persist across repeated runs — and it's wider than one route.** `lib/rate-limit.ts` is backed by Upstash Redis (persistent, not in-memory) whenever `UPSTASH_REDIS_REST_URL` is set, which it is here — restarting the dev server between runs does NOT reset it, and this Redis instance has no preview/production split (unlike Supabase's `_PREVIEW_`/`_PRODUCTION_` pair), so it's the same one production uses. `/api/inbound-email`'s limiter (10/hour) is keyed on the sender email, which every relevant e2e spec sends as `from`. Every OTHER rate limiter in the app (`trial-signup`, `cqc-lookup`, `inbound-blog-signup`, `inbound-contact`, `inbound-demo`, `inbound-waitlist`, `inbound-optout`, `support-content`) is keyed on client IP via `getClientIp()` — and since the local dev server sits behind no reverse proxy, `x-forwarded-for`/`x-real-ip` are never set on e2e traffic, so `getClientIp()` always falls back to the literal string `'unknown'`. That means every one of those limiters shares a single deterministic Redis bucket across *every* e2e run, forever. `trial-signup`'s 3/hour ceiling is the most exposed: three back-to-back reruns (exactly what the "re-run 3 times" discipline calls for) can legitimately exhaust it. Symptom looks like a real bug (`response.ok()` false, or a "Too many..." message rendered in the UI), easy to mistake for a regression — check server logs for a `Rate limit hit` line before assuming one is.

**This is now handled automatically, not a manual step to remember.** `npm run test:e2e:seed` (`e2e/support/seed.ts`, `clearStaleRateLimitKeys()`) clears every one of these buckets as part of its own "wipe and recreate" clean-slate step, the same philosophy it already applies to the DB fixture — scoped only to identifiers a real customer could never produce (this fixture's own `.invalid` sender address, and the literal `unknown` IP bucket), never a blanket flush of the rate-limit namespace. Re-seeding between repeated runs (already the fix for fixture drift, above) now fixes this too. If a rate-limit false-failure still turns up, it means a limiter name was added without being added to `IP_KEYED_LIMITER_NAMES` in `seed.ts` — add it there rather than manually clearing Redis.
